### Задание 1. Резервное копирование

### Кейс
Финансовая компания решила увеличить надёжность работы баз данных и их резервного копирования. 

Необходимо описать, какие варианты резервного копирования подходят в случаях: 

1.1. Необходимо восстанавливать данные в полном объёме за предыдущий день.

1.2. Необходимо восстанавливать данные за час до предполагаемой поломки.

1.3.* Возможен ли кейс, когда при поломке базы происходило моментальное переключение на работающую или починенную базу данных.

*Приведите ответ в свободной форме.*

### Решение 1.


1.1. Восстановление данных в полном объёме за предыдущий день
Наиболее подходящий вариант — полное (фулл) резервное копирование один раз в сутки, которое выполняется ночью, когда нагрузка на систему минимальна. Такой подход позволяет восстановить данные в точке времени «вчерашний день».

```
Реализация:

Использование pg_dump/mysqldump или физических копий (pg_basebackup, xtrabackup) с сохранением всех данных БД.

Хранение на отдельном хранилище (например, S3 или NAS).

Планирование по cron.
```
1.2. Восстановление данных за час до предполагаемой поломки
Подходит инкрементное или дифференциальное резервное копирование вместе с журналами изменений.

```
Решение для PostgreSQL:

Использование WAL-архивирования (Write-Ahead Logging).

Один раз в день — полный бэкап (pg_basebackup).

Каждый час — архивация WAL-файлов.

Позволяет восстановить БД до состояния на любой момент времени с точностью до минут.

Решение для MySQL:

Полный бэкап + binlog-файлы.
```
1.3. Возможность моментального переключения на работающую базу
Да, это возможно и называется кластеризация или репликация с автоматическим failover'ом.

```
Решения:

PostgreSQL: Patroni + Etcd + HAProxy — обеспечивает автоматический failover.

MySQL: Group Replication, Orchestrator или Percona XtraDB Cluster.

Преимущества:

Минимум простоя.

Автоматическое переключение на реплику при сбое.

Высокая доступность (HA).

Восстановление с помощью полного бэкапа и применения binlog до нужного часа.
```


### Задание 2. PostgreSQL

2.1. С помощью официальной документации приведите пример команды резервирования данных и восстановления БД (pgdump/pgrestore).

2.1.* Возможно ли автоматизировать этот процесс? Если да, то как?

*Приведите ответ в свободной форме.*


### Решение 2.

Резервное копирование:

```
bash
Копировать
Редактировать
pg_dump -U postgres -F c -b -v -f /backup/db.backup mydatabase
-F c: формат custom (удобен для pg_restore)

-b: включает бины (large objects)

-v: выводит подробности

-f: указывает файл

mydatabase: имя базы данных

Восстановление:

bash
Копировать
Редактировать
pg_restore -U postgres -d newdatabase -v /backup/db.backup
-d newdatabase: целевая база, куда восстанавливается
```
Возможна ли автоматизация?
Да. Используют:
```
cron или systemd timer для запуска по расписанию

bash-скрипты для управления копиями и логами

pgBackRest или Barman — специализированные инструменты резервного копирования PostgreSQL с поддержкой инкрементальных бэкапов, архивации WAL, проверок целостности и удалённого хранения

Пример автоматизации:

bash
Копировать
Редактировать
#!/bin/bash
DATE=$(date +%F-%H-%M)
pg_dump -U postgres -F c -b -f /backup/db-$DATE.backup mydatabase
```

*Приведите ответ в свободной форме.*

### Решение 3.

3.1. Пример команды инкрементного резервного копирования
Инкрементные бэкапы возможны только при использовании Percona XtraBackup (официально поддерживается MySQL и MariaDB):

Полный бэкап:
```
xtrabackup --backup --target-dir=/backups/full --user=root --password=123
```
Инкрементальный бэкап:
```
xtrabackup --backup --target-dir=/backups/inc1 --incremental-basedir=/backups/full --user=root --password=123
```

Преимущества реплики над обычным бэкапом
```
Репликация — это постоянно обновляемая копия базы данных. Она даёт:

Минимум простоя — можно переключиться на реплику при сбое

Разгрузка основной БД — реплику можно использовать для отчётов и аналитики

Непрерывность данных — подходит для работы с live-данными

Быстрое восстановление — не нужно разворачивать бэкап вручную

Недостаток: не защищает от логических ошибок (удаление таблицы на master = удаление на реплике)
```
